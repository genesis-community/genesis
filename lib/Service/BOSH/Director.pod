=head1 NAME

Service::BOSH::Director - Full BOSH director client with environment, config, deployment, and instance management

=head1 SYNOPSIS

  use Service::BOSH::Director;

  # Create from Vault exodus data (most common)
  my $director = Service::BOSH::Director->from_exodus(
    'my-bosh',
    $genesis_env,
  );

  # Create from local BOSH CLI config alias
  my $director = Service::BOSH::Director->from_alias(
    'my-bosh',
    $genesis_env,
  );

  # Create from current environment variables
  my $director = Service::BOSH::Director->from_environment();

  # Validate connectivity
  $director->connect_and_validate();

  # Work with configs
  my %configs = $director->configs();
  $director->upload_config(\%cloud_config, 'cloud', 'default');

  # Deploy a manifest
  $director->deployment('my-deployment');
  $director->deploy('/path/to/manifest.yml');

  # Run on a VM instance
  my $result = $director->run_on_instance(
    'cat /var/log/syslog',
    target => 'api/0',
  );

=head1 DESCRIPTION

C<Service::BOSH::Director> is the primary subclass of L<Service::BOSH> and
represents a full BOSH director with credentials, connection state, and
the complete set of BOSH operations.

Instances are typically created via L</from_exodus> (reading credentials
stored in Vault by a deployed bosh-genesis-kit environment) or via
L</from_alias> (using a local C<~/.bosh/config> entry). A lower-level
L</new> constructor is available for cases where credentials are assembled
programmatically.

The module covers six broad functional areas:

=over 4

=item Connection management

L</connect_and_validate> verifies TCP reachability and BOSH API
authorization, caching the result in C<$ENV{GENESIS_BOSH_VERIFIED}> to
avoid repeated round trips within a Genesis run.

=item Config management

L</configs>, L</has_config>, L</get_config>, L</download_configs>,
L</upload_config>, L</upload_config_from_file>, and L</delete_config>
provide full CRUD access to BOSH named configurations (cloud, runtime,
cpi, etc.).

=item Deployment management

L</deploy>, L</run_errand>, L</deployments>, L</has_deployment>,
L</delete_deployment>, and L</cleanup> cover the full deployment lifecycle.

=item Stemcell management

L</stemcells> and L</upload_stemcell> list and upload stemcells.

=item Network locking

L</network_lock_path>, L</check_network_lock>, L</acquire_network_lock>,
L</network_locked_by_me>, and L</clear_network_lock> implement a
Vault-backed mutex used to serialise network claim updates.  On a kv v2
mount the lock is taken with a check-and-set write, so exactly one of any
number of competing processes gets it; on a kv v1 mount it falls back to a
write and read-back, which is not atomic.

=item Instance operations

L</run_on_instance>, L</run_on_instances>, L</upload_to_instances>, and
L</upload_to_instance> run shell commands or upload files to BOSH-managed
VMs via C<bosh ssh> and C<bosh scp>.

=back

=head1 CLASS METHODS

=head2 new

  my $director = Service::BOSH::Director->new($alias, %opts);

Raw constructor. Parses the URL from C<opts{url}> into schema, host, and
port components, then blesses and returns a director object. Prefer the
factory methods L</from_exodus>, L</from_alias>, or L</from_environment>
over calling this directly.

The C<validated> flag is initialised from C<$ENV{GENESIS_BOSH_VERIFIED}>:
the director starts pre-validated when the environment variable matches
C<$alias>.

B<Note:> No validation is performed on the URL; a malformed URL silently
produces C<undef> for schema, host, and port (see C<url-parse-no-validate>
in L</KNOWN ISSUES>).

B<Parameters:>

=over 4

=item $alias

The BOSH director alias name (e.g. C<'prod-bosh'>).

=item %opts

A hash of options:

=over 4

=item url

The BOSH director URL (e.g. C<https://10.0.0.6:25555>). Required. Port
defaults to C<25555> when omitted from the URL.

=item env

Optional C<Genesis::Env> object associated with this director.

=item ca_cert

Optional CA certificate string for TLS verification.

=item client

BOSH client (username) for authentication.

=item secret

BOSH client secret (password) for authentication.

=item deployment

Optional default deployment name.

=item use_local_config

Boolean. When true, the BOSH CLI local config file is used rather than
director-level credentials.

=item exodus_vault

A C<Service::Vault> object for network-lock and exodus operations.
Defaults to C<Service::Vault-E<gt>current> or C<Service::Vault-E<gt>default>
when not provided.

=item exodus_path

The Vault path under which this director's exodus data is stored.

=item target

Relationship of this director to the environment: C<'self'> or C<'parent'>
(default C<'parent'>).

=back

=back

B<Returns:> A blessed C<Service::BOSH::Director> object.

B<Examples:>

  my $director = Service::BOSH::Director->new(
    'prod-bosh',
    url    => 'https://10.0.0.6:25555',
    client => 'admin',
    secret => 's3cr3t',
  );
  # Returns: a Service::BOSH::Director object

=head2 has_director

  my $bool = Service::BOSH::Director->has_director();
  my $bool = $director->has_director();

Returns C<1>. Overrides the base-class C<has_director> (in L<Service::BOSH>),
which returns C<0>, to indicate that this object represents an actual
director rather than a placeholder.

B<Returns:> C<1>

B<Examples:>

  if ($director->has_director()) {
    $director->connect_and_validate();
  }
  # Returns: 1

=head2 from_exodus

  my $director = Service::BOSH::Director->from_exodus($alias, $env, %opts);

Factory method. Constructs a director by reading connection credentials
from Vault exodus data that was written by a C<bosh-genesis-kit>
deployment.

The exodus path is derived from C<$env->bosh_env> unless explicitly
supplied via C<opts{exodus_path}>. When C<opts{rel_to_env}> is C<'self'>
the path comes from C<$env->exodus_base>; otherwise (the default C<'parent'>
behaviour) it is built from the exodus mount and deployment alias.

The exodus data is validated for the required keys C<url>,
C<admin_username>, C<admin_password>, C<ca_cert>, and C<kit_name>. The kit
must be of type C<bosh> (or the exodus data must set C<is_bosh>,
C<is_director>, or include C<director> in a C<services> list).

When C<$env->user_provided_bosh_creds_policy> is not C<'ignore'>, the
C<BOSH_USER> and C<BOSH_PASSWORD> environment variables override the exodus
credentials when both are present. When the policy is C<'require'> and
neither variable is set, the method dies.

Returns C<undef> when exodus data is not found or fails validation; these
cases are traced but not fatal.

B<Parameters:>

=over 4

=item $alias

The BOSH director alias name.

=item $env

A C<Genesis::Env> object. Required; dies if not provided or not the
correct type.

=item %opts

A hash of options:

=over 4

=item exodus_data

Pre-fetched exodus data hashref. When provided, Vault is not queried.

=item exodus_path

Override the Vault path used to retrieve exodus data.

=item exodus_mount

Override the Vault mount prefix used when building the exodus path.

=item exodus_vault

A C<Service::Vault> object to read exodus data from. Defaults to the
environment's vault.

=item rel_to_env

C<'self'> or C<'parent'> (default C<'parent'>). Controls whether the
exodus path points to the environment's own deployment or to its
parent BOSH director.

=item bosh_deployment_type

Override for the BOSH deployment type suffix in the exodus path.
Defaults to the C<dep_type> from C<$env->bosh_env>, then C<'bosh'>.

=item deployment

Optional default deployment name for the returned director.

=back

=back

B<Returns:> A C<Service::BOSH::Director> object on success, or C<undef>
when exodus data is absent or fails validation.

B<Errors:>

Dies with C<"Require an env object - was not passed in"> when C<$env> is
missing or not a C<Genesis::Env>.

Dies with C<"Must provide BOSH credentials via environment variables BOSH_USER and BOSH_PASSWORD">
when C<$env->user_provided_bosh_creds_policy> is C<'require'> and neither
C<BOSH_USER> nor C<BOSH_PASSWORD> is set.

B<Examples:>

  my $director = Service::BOSH::Director->from_exodus(
    'prod-bosh',
    $env,
  );
  if ($director) {
    $director->connect_and_validate();
  }
  # Returns: a Service::BOSH::Director object, or undef

  # Use self-deployment exodus data
  my $director = Service::BOSH::Director->from_exodus(
    'my-bosh',
    $env,
    rel_to_env => 'self',
  );
  # Returns: a Service::BOSH::Director object, or undef

=head2 from_alias

  my $director = Service::BOSH::Director->from_alias($alias, $env, %opts);

Factory method. Constructs a director using an alias entry from the local
BOSH CLI configuration file (C<~/.bosh/config> by default). The config
file is parsed as YAML and searched for an environment entry whose
C<alias> field matches C<$alias>.

Returns C<undef> when the config file does not exist or no matching
alias is found.

B<Parameters:>

=over 4

=item $alias

The BOSH director alias to look up in the config file.

=item $env

An optional C<Genesis::Env> object stored on the resulting director.

=item %opts

A hash of options:

=over 4

=item config_home

Override the path to the BOSH config file. Defaults to
C<$ENV{HOME}/.bosh/config>.

=item deployment

Optional default deployment name for the returned director.

=back

Any additional options are passed through to L</new>.

=back

B<Returns:> A C<Service::BOSH::Director> object on success, or C<undef>
when the config file is absent or the alias is not found.

B<Errors:>

=over 4

=item *

Calls C<bug()> with C<"from_alias() called without an alias"> when C<$alias>
is falsy.

=back

B<Examples:>

  my $director = Service::BOSH::Director->from_alias('prod-bosh', $env);
  if ($director) {
    print "Found director at: ", $director->url(), "\n";
  }
  # Returns: a Service::BOSH::Director object, or undef

=head2 from_environment

  my $director = Service::BOSH::Director->from_environment();

Factory method. Constructs a director from the current set of BOSH
environment variables.

When C<$ENV{BOSH_ENVIRONMENT}> is a valid URI and C<$ENV{BOSH_CLIENT}> is
set, the director is created directly from C<BOSH_ENVIRONMENT>,
C<BOSH_CLIENT>, C<BOSH_CLIENT_SECRET>, C<BOSH_CA_CERT>, C<BOSH_ALIAS>,
and C<BOSH_DEPLOYMENT>.

Otherwise, falls back to L</from_alias> using C<$ENV{BOSH_ALIAS}> (or
C<$ENV{BOSH_ENVIRONMENT}> as the alias name) and C<$ENV{BOSH_DEPLOYMENT}>.

B<Returns:> A C<Service::BOSH::Director> object, or C<undef> if no
matching alias is found in the fallback path.

B<Examples:>

  # With BOSH_ENVIRONMENT set to a valid URI
  local $ENV{BOSH_ENVIRONMENT} = 'https://10.0.0.6:25555';
  local $ENV{BOSH_CLIENT}      = 'admin';
  local $ENV{BOSH_CLIENT_SECRET} = 's3cr3t';
  my $director = Service::BOSH::Director->from_environment();
  # Returns: a Service::BOSH::Director object

B<Errors:>

Dies with C<"No exodus vault set for BOSH director"> when no exodus vault

B<Examples:>

B<Errors:>

B<Examples:>

  # Returns: 'secret/exodus/prod/bosh'

=head2 has_config_of_type

  my $bool = $director->has_config_of_type($type);

Returns true when the director has at least one config of C<$type> uploaded.

Derived from the cached C<configs> listing, so it costs no BOSH round trip
beyond the initial fetch.  Use it to short-circuit paths that only matter when
configs of a type exist -- notably the CPI checks on single-iaas environments,
where no named cpi configs are uploaded at all.

B<Parameters:>

=over 4

=item B<$type>

Config type, e.g. C<'cloud'>, C<'runtime'>, C<'cpi'>.

=back

B<Returns:> C<1> or C<0>.  C<0> when C<$type> is undefined.

B<Examples:>

  $director->has_config_of_type('cpi');
  # Returns: 0 on a single-iaas director

=head2 config_names_of

  my @names = $director->config_names_of($type);

Returns the sorted BOSH C<--name=> identifiers for configs of C<$type>.  For
cpi configs these are B<cpi config names>, with C<default> appearing literally
when a config was uploaded without C<--name>.

B<Parameters:>

=over 4

=item B<$type>

Config type, e.g. C<'cloud'>, C<'runtime'>, C<'cpi'>.

=back

B<Returns:> A sorted list of name strings; empty when C<$type> is undefined or
nothing of that type is uploaded.

B<Examples:>

  $director->config_names_of('cpi');
  # Returns: ('aws-bundle', 'vsphere-prod')

B<Limitations:> These are B<not> the cpi names appearing inside a cpi config's
C<cpis[]> array, and not the director's own latent CPI (L</cpi>).  Conflating
the three is a recurring source of bugs; see L</cpi> for the distinction.

=head2 director_info

  my $info = $director->director_info();

Returns the director's own summary as reported by C<bosh env --json>, as a
hashref keyed by the snake_cased column titles: C<name>, C<uuid>, C<version>,
C<director_stemcell>, C<cpi>, C<features>, C<user>.

Populated as a side effect of L</status>, which already makes this call for
its reachability and authorization check -- retaining the row costs nothing
extra.  If something asks before the director has been contacted, the query
happens on demand.

B<Returns:> A hashref.  Empty (C<{}>) when the director could not be reached
or did not answer with a parseable table.

B<Examples:>

  print $director->director_info->{version};
  # Returns: '280.0.23 (00000000)'

B<Limitations:> An unreachable director memoizes an empty hashref rather than
re-querying on every access, so a director that becomes reachable later will
keep reporting empty within the same process.  C<features> arrives as a
newline-joined string (C<"config_server: enabled\nlocal_dns: enabled">), not
as structured data.  Named C<director_info> rather than C<info> because
C<Genesis> exports an C<info> logging function into this package.

=head2 cpi

  my $cpi = $director->cpi();

Returns the director's latent CPI -- the CPI B<release> it runs, such as
C<vsphere_cpi> or C<warden_cpi>.  Convenience wrapper over
L</director_info>.

B<Returns:> A string, or C<undef> when unknown.

B<Examples:>

  print $director->cpi();
  # Returns: 'vsphere_cpi'

B<Limitations:> This is a third kind of name, distinct from both a B<cpi
config name> (the C<--name=> on C<bosh update-config --type=cpi>, defaulting
to C<default>) and a B<cpi name> (the C<name:> of an entry in a cpi config's
C<cpis[]> list, sentinel C<< <default> >>).  It identifies the IaaS the
director itself talks to, so it cannot satisfy an C<az_map> reference or any
other named-cpi lookup.  Treat it as reporting only.

B<Examples:>

=head2 environment_variables

  my %vars = $director->environment_variables();

Returns a hash of BOSH environment variables describing this director.
Overrides the base-class C<environment_variables> method in L<Service::BOSH>.

The returned hash always contains:

=over 4

=item C<BOSH_ALIAS>

The director alias.

=item C<BOSH_ENVIRONMENT>

The director URL.

=item C<BOSH_CA_CERT>

The CA certificate.

=item C<BOSH_CLIENT>

The client username.

=item C<BOSH_CLIENT_SECRET>

The client secret.

=item C<BOSH_REL_TO_ENV>

The relationship to the associated Genesis environment (C<'parent'> by
default).

=item C<BOSH_USER>

Always set to C<undef> (clears any inherited value).

=item C<BOSH_PASSWORD>

Always set to C<undef> (clears any inherited value).

=back

When both an exodus path and exodus vault are configured, the hash also
contains C<BOSH_EXODUS_PATH> and C<BOSH_EXODUS_VAULT>.

When a deployment name is set, C<BOSH_DEPLOYMENT> is included.

B<Returns:> A flat hash (not a reference) of variable name to value.

B<Examples:>

  my %vars = $director->environment_variables();
  # Returns: (
  #   BOSH_ALIAS          => 'prod-bosh',
  #   BOSH_ENVIRONMENT    => 'https://10.0.0.6:25555',
  #   BOSH_CA_CERT        => '-----BEGIN CERTIFICATE-----...',
  #   BOSH_CLIENT         => 'admin',
  #   BOSH_CLIENT_SECRET  => 's3cr3t',
  #   BOSH_REL_TO_ENV     => 'parent',
  #   BOSH_USER           => undef,
  #   BOSH_PASSWORD       => undef,
  # )

=head2 connect_and_validate

  my $director = $director->connect_and_validate();

Verifies that the BOSH director is reachable and that the configured
credentials are authorised. Overrides the base class method.

Returns C<$self> immediately when the director is already marked
validated (either from a previous call or from C<$ENV{GENESIS_BOSH_VERIFIED}>
at construction time).

Delegates to L</status> which, on success, sets
C<$self-E<gt>{validated}> to C<1> and C<$ENV{GENESIS_BOSH_VERIFIED}> to
the director alias.

B<Returns:> The director object (C<$self>).

B<Errors:>

Dies with C<"Unable to connect to #M{%s} BOSH director:\n%s - %s"> when
the status is C<error> or C<unreachable>. C<%s> placeholders are the alias,
the status string, and the error message.

Dies with C<"Unable to connect to #M{%s} BOSH director: no active session.  Please log in and try again.">
when the status is C<unauthorized>. C<%s> is the alias.

B<Examples:>

  my $director = Service::BOSH::Director->from_exodus('prod-bosh', $env);
  $director->connect_and_validate();
  # Returns: $director (or dies on connection failure)

=head2 status

  my $hashref = $director->status();

Probes the BOSH director and returns a status hashref. Does not require
prior validation.

When C<$ENV{BOSH_ALL_PROXY}> is set, the probe runs C<bosh env> via the
proxy and applies a timeout from C<$ENV{GENESIS_NETWORK_TIMEOUT}> (default
10 seconds). Otherwise, TCP reachability to the director's host and port
is checked first with a plain socket test.

On success, the authenticated user is extracted from the C<bosh env>
output and stored in C<$self-E<gt>{user}>, C<$self-E<gt>{validated}> is
set to C<1>, and C<$ENV{GENESIS_BOSH_VERIFIED}> is set to
C<$self-E<gt>{alias}>.

B<Returns:> A hashref with keys:

=over 4

=item status

One of C<'ok'>, C<'unreachable'>, C<'error'>, or C<'unauthorized'>.

=item msg

A human-readable message describing the status.

=back

B<Errors:>

When C<BOSH_ALL_PROXY> is set and the proxy timeout fires, the ALRM
signal handler raises C<"timeout\n"> internally. This is caught and
results in a C<< { status => 'unreachable', msg => "timeout after N seconds" } >>
return value rather than propagating as an exception.

B<Examples:>

  my $s = $director->status();
  if ($s->{status} eq 'ok') {
    print "Director is up: $s->{msg}\n";
  }
  # Returns: { status => 'ok', msg => 'authorized as admin' }

=head2 configs

  my %configs  = $director->configs(%opts);   # list context
  my $configs  = $director->configs(%opts);   # scalar context

Lists all configurations on the BOSH director.

The listing is memoized on first call, so repeated queries during one
Genesis run cost a single C<bosh configs> invocation.

In list context, returns a flat hash. In scalar context, returns a
reference to the same hash.

B<Parameters:>

=over 4

=item %opts

=over 4

=item C<refresh>

Discard the memoized listing and re-query the director. Needed after an
upload or delete, since the cache would otherwise still describe the
director as it was.

=back

=back

The returned structure is nested:

  {
    $type => {
      $name => {
        current => $id,          # ID of the currently active version
        entries => {
          $id => {
            date => $created_at,
            team => $team,
          },
        },
      },
    },
  }

B<Returns:> In list context, a hash. In scalar context, a hashref.

B<Examples:>

  my %configs = $director->configs();
  for my $type (sort keys %configs) {
    for my $name (sort keys %{$configs{$type}}) {
      print "  $type/$name (current: $configs{$type}{$name}{current})\n";
    }
  }
  # Returns: ('cloud' => { default => { current => '3', entries => {...} } }, ...)

=head2 has_config

  my $bool = $director->has_config($type, $name);

Returns true when the BOSH director has a configuration of the given type
and name.

B<Parameters:>

=over 4

=item $type

The configuration type (e.g. C<'cloud'>, C<'runtime'>, C<'cpi'>).

=item $name

The configuration name (e.g. C<'default'>).

=back

B<Returns:> True when the configuration exists, false otherwise.

B<Examples:>

  if ($director->has_config('cloud', 'default')) {
    my $content = $director->get_config('cloud', 'default');
  }
  # Returns: 1 if the cloud/default config exists

=head2 get_config

  my $content = $director->get_config($type, $name, %opts);

Returns the content string of the named configuration, or C<undef> when
no matching configuration is found.

Memoized per C<(type, name)> pair. A C<undef> result is cached as well as
a hit, so a config that did not exist is not re-queried on every call --
which is why C<upload_config_from_file> explicitly invalidates this cache
for the pair it just uploaded.

B<Parameters:>

=over 4

=item $type

The configuration type (e.g. C<'cloud'>, C<'runtime'>).

=item $name

The configuration name.

=item %opts

=over 4

=item C<refresh>

Discard the memoized content for this C<(type, name)> and re-query.

=back

=back

=head2 cpis

  my @names = $director->cpis(%opts);   # list context
  my $names = $director->cpis(%opts);   # scalar context

The names of every CPI defined across all of the director's cpi configs.

This is the live inventory, read from the director rather than from what
Genesis believes it advertised. Each cpi config is fetched and parsed, and
the C<name> field of each entry in its C<cpis> array is collected;
the union is returned sorted and de-duplicated.

Exodus is deliberately B<not> used as a fast path here. Exodus records only
what Genesis advertised at deploy time, and cpi configs may have been
uploaded out of band -- which is routine outside OCFP. The director's own
state is the authoritative answer to "what CPIs are available here?". In
that respect this is a sibling of C<stemcells>: a fact about the director,
not about any environment that consumes it.

Failures are swallowed deliberately -- a config that cannot be fetched,
does not parse, or has no C<cpis> array contributes nothing rather than
aborting the inventory. A director with no cpi configs yields an empty
list, not an error.

Note that a I<cpi name> here is the C<name> of an entry inside a cpi
config, not the name the cpi config itself was uploaded under. One cpi
config may contribute several.

B<Parameters:>

=over 4

=item %opts

=over 4

=item C<refresh>

Discard the memoized inventory and re-read every cpi config.

=back

=back

B<Returns:> In list context, a sorted list of cpi name strings. In scalar
context, an arrayref of the same.

B<Examples:>

  my @cpis = $director->cpis;
  # Returns: ('aws-us-east-1', 'aws-us-west-2', 'vsphere-dc1')

  my @cpis = $director->cpis(refresh => 1);
  # Returns: the same, re-read from the director

  # Director with no cpi configs:
  my @cpis = $director->cpis;
  # Returns: ()

=head2 download_configs

  my @configs  = $director->download_configs($path, $type, $name, %opts);
  my $configs  = $director->download_configs($path, $type, $name, %opts);

Downloads one or more configurations to C<$path> on the local filesystem.

When C<$name> is C<'*'> (or omitted), all configs of the given type are
fetched and assembled into a single file. Otherwise the single named
config is written directly.

B<Assembly differs by type.> For most types the long-standing
C<spruce merge> behaviour is correct: merge-by-name on keyed entries
(C<azs>, C<networks>, C<vm_types>, C<addons>, C<releases>, ...) mirrors
how BOSH composes them at deploy time.

C<cpi> is the exception. BOSH concatenates the C<cpis> arrays across all
active cpi configs and B<errors on duplicate cpi names>. Spruce's
merge-by-name would silently dedupe exactly those duplicates and hide the
divergence, so cpi takes a manual concatenation path instead: each config
is parsed, the C<cpis> arrays are concatenated, and a duplicate cpi name
bails locally with the offending name attributed to the cpi configs it
came from. That is more actionable than waiting for BOSH's terser
duplicate-name error at deploy time.

Note the distinction the error message keeps: the B<cpi config name> is
what the config was uploaded as, while the B<cpi name> is the C<name>
field of an entry inside its C<cpis> array. It is duplicate I<cpi names>
that BOSH rejects, and one cpi config can contribute several.

B<Results are memoized.> The assembled output is written to a
director-internal cache path and then copied to C<$path>; later calls for
the same C<(type, name)> pair pay only the copy. Pass C<< refresh => 1 >>
to discard that cache.

Each config entry in the returned list is a hashref with keys:

=over 4

=item type

The configuration type.

=item name

The configuration name.

=item label

A human-readable label (e.g. C<'default cloud config'> or C<"cloud config 'extra'">).

=back

B<Parameters:>

=over 4

=item $path

The local filesystem path where the merged config file will be written.

=item $type

The configuration type to download.

=item $name

Optional. The configuration name to download. Defaults to C<'*'> (all
configs of the given type).

=item %opts

=over 4

=item C<refresh>

Discard the cached assembly for this C<(type, name)> and re-fetch. The
config I<listing> is refreshed unconditionally too, even when a specific
name was requested -- that name may be a fresh upload absent from the
cached listing.

=item C<optional>

When no configs of C<$type> exist on the director, return empty instead
of bailing. Single-IaaS environments with no named cpi configs rely on
this; without it the legacy bail stands.

=back

=back

B<Returns:> In list context, a list of config entry hashrefs. In scalar
context, an arrayref of the same entries. With C<< optional => 1 >> and no
matching configs, an empty list or arrayref.

B<Errors:>

Dies with C<"No matching %s configurations defined on '#M{%s}' BOSH director">
when no configs of the type exist and C<optional> was not set, or when the
downloaded file is empty. C<%s> is the config type and the director alias.

Dies with C<"No $c->{label} contents."> when a fetched configuration entry
has empty content. C<$c-E<gt>{label}> is the human-readable label of the
config entry (e.g. C<"default cloud config">).

Dies with C<"Duplicate cpi name(s) found across uploaded cpi configs on '#M{%s}' BOSH director:">
followed by each duplicated cpi name and the cpi configs it appears in,

refuse to deploy until the duplicate is resolved, by deleting the

Dies with C<"Failed to converge the active $type configurations: $err"> when
C<spruce merge> fails while merging multiple non-cpi configs. C<$type> is
the config type and C<$err> is the error output.

B<Examples:>

  my @entries = $director->download_configs('/tmp/cloud.yml', 'cloud');
  for my $e (@entries) {
    print "Downloaded: $e->{label}\n";
  }
  # Returns: ({ type => 'cloud', name => 'default', label => 'default cloud config' }, ...)

  # Tolerate a director with no cpi configs at all.
  my @entries = $director->download_configs(
    '/tmp/cpi.yml', 'cpi', '*', optional => 1,
  );
  # Returns: () when the director has no cpi configs

  # Force a re-fetch after uploading a new config.
  my @entries = $director->download_configs(
    '/tmp/cpi.yml', 'cpi', '*', refresh => 1,
  );
  # Returns: the entries, with both the listing and assembly re-read

=head2 check_network_lock

  my $result = $director->check_network_lock(%opts);

Reads the network claims lock at L</network_lock_path> with
C<Service::Vault::kv_read> and returns a status hashref.

The lock is C<'unlocked'> when no record exists, or when the record has no
C<at> field, which is what a released lock on a kv v2 mount looks like.  A
held lock is C<'stale'> once its age exceeds C<max_lock_age>, or as soon as
its process has exited when that process ran on this same host.  Otherwise
it is C<'locked'>.

A vault that cannot be read is an error, not an unlocked director, so that
a sealed or unreachable vault never lets a second deploy through.

B<Parameters:>

=over 4

=item %opts

A hash of options:

=over 4

=item max_lock_age

Maximum age in seconds before a lock is considered stale. Defaults to
C<1800> (30 minutes).

=back

=back

B<Returns:> A hashref with these keys, of which C<status>, C<path>,
C<version>, and C<kv_version> are always present:

=over 4

=item status

C<'unlocked'>, C<'locked'>, or C<'stale'>.

=item path

The lock's vault path, from L</network_lock_path>.

=item version

On a kv v2 mount, the version of the lock secret that was read, which is
C<0> when it has never been written.  A check-and-set write must name it.
C<undef> on a kv v1 mount.

=item kv_version

C<1> or C<2>, the version of the kv mount the lock is on.

=item lock

The lock record (absent when unlocked).  Contains C<at>, C<user>,
C<hostname>, C<pid>, C<env>, and C<token>.

=item age

The age of the lock in seconds (absent when unlocked).

=item max_age

The C<max_lock_age> the status was judged against (absent when unlocked).

=item description

A human-readable string describing when and by whom the lock was taken
(absent when unlocked).

=back

B<Errors:>

Dies through C<Service::Vault::kv_read> or C<Service::Vault::kv_mount>
when the vault refuses the read or cannot be reached, naming the path and
the likely causes.

B<Examples:>

  my $result = $director->check_network_lock();
  if ($result->{status} eq 'unlocked') {
    $director->acquire_network_lock();
  } elsif ($result->{status} eq 'stale') {
    warn "Stale lock detected: $result->{description}\n";
  }
  # Returns: { status => 'unlocked', path => '...', version => 3, kv_version => 2 }
  #       or { status => 'locked', lock => {...}, age => 42, description => '...', ... }

=head2 acquire_network_lock

  my $lock = $director->acquire_network_lock(%opts);

Takes the network claims lock by writing a lock record to
L</network_lock_path>, after checking that an older Genesis does not hold
the older form of the lock (see L</_refuse_legacy_network_lock>).  The
record holds the time, hostname, user, PID, environment name, and a token
that marks it as this process's own (see L</_network_lock_token>).  The time is written in UTC with a C<+0000>
offset, so that a reader on any host works out the same age for it.  A
stale lock is taken over, with a note saying whose it was.

How the write is made depends on the kv mount the lock is on:

=over 4

=item kv v2

The write is a check-and-set write that names the version
L</check_network_lock> just read.  However many processes read the same
version, the vault lets only the first write through.  Every other writer
is refused, reads the lock again, and stops with a message naming the
holder and saying that it lost the race.  This is atomic.

=item kv v1

kv v1 has no check-and-set write, so this is not atomic.  The method
writes the lock, waits C<$Service::BOSH::Director::NETWORK_LOCK_SETTLE_SECONDS>
seconds (2 by default), and reads it back.  If another process's lock is
there instead, that process's write landed last and this one stops.  A
competing write slower than the wait can still go unnoticed, so the method
warns once per lock path that the lock is best-effort.

=back

B<Parameters:>

=over 4

=item %opts

Passed to L</check_network_lock>, so C<max_lock_age> applies.

=back

B<Returns:> The lock record that was written.

B<Errors:>

=over 4

=item *

Dies when another process holds a lock that is not stale.  The message
names the director, the holder's user, host, environment, and PID, when
the lock was taken, the vault path and URL, the likely cause, and how
long until the lock goes stale.  When this process lost a race for the
lock, the message says so.

=item *

Dies when an older Genesis holds the older form of the lock, or when the
vault will not say whether one does, through
L</_refuse_legacy_network_lock>.  Nothing is written in either case.

=item *

On kv v1, dies when the read-back finds no lock at all, which means
another process released it in that moment or the vault target is a
standby node whose reads lag the leader.

=item *

Dies when the lock record changes between every read and write in five
attempts.

=item *

Dies when the write of the lock fails, through L</_write_network_lock>.
The vault may have accepted the write before the failure, so the message
says that this process may now hold the lock, that it is released as the
command exits, and how to check for it and clear it by hand.  A signal
that arrives during the write passes through unchanged.

=item *

Vault failures from C<Service::Vault::kv_read> propagate.

=back

B<Examples:>

  my $lock = $director->acquire_network_lock();
  # Returns: { at => '2026-10-05 15:03:41 +0000', user => 'ops', token => '...', ... }
  # Lock is now held; release it when done:
  $director->clear_network_lock();
  # Returns: 1

=head2 network_locked_by_me

Returns true when the current process holds the network claims lock, which
it tells by comparing the lock's C<token> with L</_network_lock_token>.  A

B<Errors:>

Vault failures from L</check_network_lock> propagate.

B<Examples:>

  if ($director->network_locked_by_me()) {
    # Safe to update network config
    $director->clear_network_lock();
  }
  # Returns: 1 if this process holds the lock, 0 otherwise

=head2 clear_network_lock

  my $cleared = $director->clear_network_lock(%opts);

Releases the network claims lock, but only the lock that was asked about.
With no options, that is this process's own lock.  With C<stale>, it is
the very record that L</check_network_lock> reported as stale; a lock that
has changed hands since then is someone else's and is left alone.

On a kv v2 mount the lock is released by a check-and-set write of a record
with no holder in it, because kv v2 has no check-and-set delete and a plain
delete could remove a lock that another process wrote after the read.  On a
kv v1 mount, which refuses a record with no fields, the lock secret is
deleted with C<Service::Vault::kv_delete>, so that a delete the vault
refuses is an error rather than a quiet no-op.

B<Parameters:>

=over 4

=item %opts

A hash of options:

=over 4

=item stale

The status hashref from L</check_network_lock> that reported the lock as
stale.  The lock is cleared only while it is still that record: the same
version on kv v2, or the same lock fields on kv v1.

=back

=back

B<Returns:> C<1> when the lock was cleared, C<0> when there was nothing to
clear or the lock was not the one asked about.

B<Errors:>

Dies when the lock record changes between every read and write in five
attempts, naming the director, the path, and the vault.  Vault failures
from L</check_network_lock>, C<Service::Vault::kv_write>, and
C<Service::Vault::kv_delete> propagate, so a release the vault refuses is
never counted as done.

B<Examples:>

  $director->clear_network_lock();
  # Returns: 1 if this process's lock was released, 0 otherwise

  my $current = $director->check_network_lock();
  $director->clear_network_lock(stale => $current) if $current->{status} eq 'stale';
  # Returns: 1, or 0 if another process took the lock in the meantime

=head2 ensure_network_lock_held

  $director->ensure_network_lock_held($action);

Stops unless this process still holds the network claims lock.  Call it
just before a step that the lock protects, such as uploading the cloud
config or writing the network claims.  This process can lose the lock
while it waits, most often at a prompt, for longer than the lock's stale
timeout, because another deploy or C<bosh-configs upload> then clears the
lock as stale and may take it.

While this process does hold its lock, it also reads the older form of the
lock again, with L</_refuse_legacy_network_lock>.  An older Genesis that
started after this process took its lock never looks at that lock, so this
is the last point before the write at which the two can be told apart.  It
narrows the window in which both write claims, and cannot close it, because
an older Genesis can still take its own lock just after the check.

B<Parameters:>

=over 4

=item C<$action>

What this process was about to do, as a phrase that follows "Cannot", such
as C<'upload the cloud config'>.  The message uses it twice.

=back

B<Returns:> C<1> when this process holds the lock.

B<Errors:>

=over 4

=item *

Dies when this process holds its lock but an older Genesis holds the older
form of it, or the vault will not say whether one does.  The messages are
those of L</_refuse_legacy_network_lock>, with C<$action> in place of taking
the lock.  Nothing is written.

=item *

Dies when this process no longer holds the lock.  The message names the
action, the director, and whether the lock is now free or held by another
process, and if so whose it is and when it was taken.  It also gives the
likely cause, says to run the command again once the other process has
finished, and names the lock's path and the C<safe get> command that shows
it.

=item *

Vault failures from L</check_network_lock> propagate.

=back

B<Examples:>

  $director->ensure_network_lock_held('upload the cloud config');
  # Returns: 1, or dies when another process has taken the lock

=head2 release_network_lock

  my $released = $director->release_network_lock();

Releases the network claims lock if this process holds it, for the cleanup
that runs as a command finishes, fails, or is interrupted.  It never dies,
so a failed release cannot replace the error that stopped the caller, nor
stop the caller releasing its locks on other directors.  A release that
fails is logged with the director, the reason, when other deploys can take
the lock, the likely causes, and what to check.

While it runs, C<INT>, C<TERM>, C<HUP>, and C<QUIT> are blocked, and the
processes it starts inherit that.  A terminal sends Ctrl-C to every process
in its foreground group, and a dropped ssh session sends C<HUP> to every
process in it, so the C<safe> child of a vault call would otherwise be
killed, the release would fail, and the lock would stay on the director.
A signal that arrives meanwhile stays pending in this process, and reaches
the handler the caller installed once the release is over.

The log says which step failed.  When the lock could not be read, nothing
was released and it is not known whether this process holds a lock, so the
message says that, and gives the C<safe get> command that shows the lock,
the host and PID that make it this process's, and the C<safe rm> command
that clears it.  Only a failure of the clear itself is logged as a lock
that could not be released.

B<Returns:> C<1> when the lock was released.  C<0> when this process did
not hold it, including when another process took it between the check and
the clear, which is reported on the output.  C<undef> when the release
failed and was logged.

B<Examples:>

  $director->release_network_lock();
  # Returns: 1, 0 when there was nothing of ours to release, or undef on a logged failure

=head2 run_on_instance

  my ($result, $rc, $err) = $director->run_on_instance($command, %opts);  # list, non-interactive
  my $result               = $director->run_on_instance($command, %opts);  # scalar, non-interactive
  my $result               = $director->run_on_instance($command, %opts);  # interactive

Runs a shell command on a single BOSH-managed VM instance via C<bosh ssh>.

The target is specified via C<opts{target}> in C<"group/index"> or
C<"group"> form. When no index is given, index C<0> is used.

In interactive mode (C<opts{interactive}> true), the command streams
directly to the terminal. The return value is always a hashref with keys
C<stdout>, C<exit_code>, C<instance>, and C<interactive>.

In non-interactive mode, C<bosh ssh --json --results> is used and the
structured output is parsed. In list context, returns
C<($result_hashref, $rc, $err)>. In scalar context, returns only the
result hashref.

B<Parameters:>

=over 4

=item $command

The shell command to run on the target instance.

=item %opts

A hash of options:

=over 4

=item target

Required. The target instance in C<"group/index"> or C<"group"> form.
When no index is specified, defaults to index C<0>.

=item interactive

Boolean. When true, the command runs interactively and output is streamed
to the terminal. Defaults to C<0>.

=item stderr

Boolean. When true, standard error is captured separately. Defaults to
C<0>. Only used in non-interactive mode.

=back

=back

B<Returns:> In interactive mode, a hashref with C<stdout>, C<exit_code>,
C<instance>, and C<interactive>. In non-interactive list context, a
three-element list C<($result, $rc, $err)> where C<$result> is a hashref
of the parsed BOSH JSON output row. In non-interactive scalar context, the
result hashref only.

B<Errors:>

Dies with C<"No command provided in call to run_on_instance()"> when
C<$command> is not provided.

Dies with C<"No target specified"> when C<opts{target}> is not set.

B<Examples:>

  # Non-interactive
  my $result = $director->run_on_instance(
    'cat /var/log/syslog',
    target => 'api/0',
  );
  # Returns: hashref with stdout, exit_code, etc.

  # Interactive
  $director->run_on_instance(
    '/bin/bash',
    target      => 'api/0',
    interactive => 1,
  );
  # Returns: { stdout => '', exit_code => 0, instance => 'api/0', interactive => 1 }

=head2 run_on_instances

  my $results = $director->run_on_instances($command, %opts);

Runs a shell command on multiple BOSH-managed VM instances via
C<bosh ssh>.

When C<opts{targets}> is empty or absent, the command is run across all
VMs in the deployment in a single C<bosh ssh> call. Otherwise, the
command is run on each target in turn and results are accumulated.

B<Parameters:>

=over 4

=item $command

The shell command to run on each target instance.

=item %opts

A hash of options:

=over 4

=item targets

Optional. An arrayref (or single string) of instance targets in
C<"group/index"> or C<"group"> form. When empty or absent, the command
runs on all VMs.

=item stderr

Boolean. When true, standard error is captured. Defaults to C<0>.

=back

=back

B<Returns:> An arrayref of result row hashrefs from the parsed BOSH JSON

B<Errors:>

Dies with C<"No command provided in call to run_on_instances()"> when

B<Examples:>

  );
  # Returns: arrayref of result hashrefs

=head2 upload_to_instances

=head1 INTERNAL METHODS

=head2 _derive_exodus_pointers

  my ($path, $vault) = $class->_derive_exodus_pointers($alias, $env, %opts);

Works out which exodus path and which vault a director's data should be
read from. Shared by the C<from_*> constructors so they agree on the
answer.

Explicit C<exodus_path> and C<exodus_vault> options always win. With no
C<$env> to consult, they are returned unchanged -- including when both are
C<undef>.

Otherwise the C<rel_to_env> option decides whose exodus is meant:

=over 4

=item C<'self'>

The environment's own exodus. Path is C<< $env->exodus_base >> and the
vault is the environment's own.

=item C<'parent'> (default)

The exodus of the BOSH director this environment deploys I<through>,
assembled as C<< mount . alias . '/' . deployment_type >>. Each part falls
back in turn: the explicit option, then the environment's C<bosh_env>
record, then the environment's own value -- with the deployment type
defaulting to C<'bosh'>.

=back

B<Parameters:>

=over 4

=item C<$alias>

The director alias, used to build the parent-relative path.

=item C<$env>

A C<Genesis::Env>, or a false value to skip derivation entirely.

=item C<%opts>

C<exodus_path>, C<exodus_vault>, C<exodus_mount>, C<bosh_deployment_type>,
and C<rel_to_env> as described above.

=back

B<Returns:> The two-element list C<($exodus_path, $exodus_vault)>.

B<Examples:>

  # Parent-relative (the default).
  my ($p, $v) = $class->_derive_exodus_pointers('prod-bosh', $env);
  # Returns: ('secret/exodus/prod-bosh/bosh', $env->vault-ish)

  # The environment's own exodus.
  my ($p, $v) = $class->_derive_exodus_pointers('x', $env, rel_to_env => 'self');
  # Returns: ($env->exodus_base, $env->vault)

  # No env: explicit values pass straight through.
  my ($p, $v) = $class->_derive_exodus_pointers('x', undef, exodus_path => 'a/b');
  # Returns: ('a/b', undef)

=head2 _write_network_lock

  my $written = $self->_write_network_lock($path, $lock, $max_age, %opts);

Writes the network claims lock record with C<Service::Vault::kv_write>.  A
write can fail after the vault has accepted it, for instance when reads on
an HA vault never catch up with the new version, and then this process may
hold the lock without knowing it.  So a failure here stops with the
original error and a note on how to find and clear the lock.

B<Parameters:>

=over 4

=item C<$path>

The lock's vault path, from L</network_lock_path>.

=item C<$lock>

The lock record to write.  Its C<hostname> and C<pid> are named in the
note.

=item C<$max_age>

The stale timeout in seconds, which the note gives in minutes.  Defaults
to C<1800>.

=item C<%opts>

Passed to C<Service::Vault::kv_write>, so C<cas> applies on kv v2.

=back

B<Returns:> What C<Service::Vault::kv_write> returned, which is C<0> for a
refused check-and-set write.

B<Errors:>

Dies when the write fails, with the original error followed by a note
that this process may now hold the lock.  The note says that the lock is
released as the command exits, when it goes stale if that release fails,
and the C<safe get> and C<safe rm> commands that check and clear it.  A
signal (C<Interrupted by user>, C<Terminated>, C<Hung up>, or C<Quit>)
passes through unchanged, for the caller's release to handle.

B<Examples:>

  my $version = $self->_write_network_lock($path, $lock, 1800, cas => 3);
  # Returns: 4, or 0 when another process wrote first

=head2 _network_lock_freshness

  my ($status, $age) = $self->_network_lock_freshness($lock, $max_age);

Works out whether a network claims lock record is still held or has gone
stale.  A lock is stale when it is older than C<$max_age> seconds, or when
it was taken on this host by a process that is no longer running, since
that process can never release it.  A lock from another host is judged by
its age alone.  It is shared by L</check_network_lock>, which judges the
current lock with it, and L</_refuse_legacy_network_lock>, which judges the
older form of the lock with the same rule.

B<Parameters:>

=over 4

=item C<$lock>

The lock record, with an C<at> time in C<%Y-%m-%d %H:%M:%S %z> form, and
optionally C<hostname> and C<pid>.

=item C<$max_age>

The stale timeout in seconds.

=back

B<Returns:> The status, which is C<'stale'> or C<'locked'>, and the age of
the lock in seconds.

B<Errors:>

Dies when C<at> is missing or is not in the expected form.

B<Examples:>

  my ($status, $age) = $self->_network_lock_freshness($lock, 1800);
  # Returns: ('locked', 42)

=head2 _refuse_legacy_network_lock

  $self->_refuse_legacy_network_lock($max_age, $action);

Stops the acquire of the network claims lock while an older Genesis holds
the older form of it.  This guards against older Genesis versions during a
rollout.  They keep the lock as a JSON string in the C<network-claim-lock>
key of the director's exodus secret, and never read the secret that
L</network_lock_path> names, so without this check the older and the newer
Genesis could each take their own lock and both write claims.

The key is read once, with C<Service::Vault::kv_read>, and is never
written or deleted.  A lock there that is still fresh by the older code's
own rule, as L</_network_lock_freshness> applies it, refuses the acquire.
A lock that is stale, a key or field that is absent, and an exodus secret
that does not exist all let the acquire go on.  A value that is not JSON,
or has no C<at> time, is not a lock record that any older Genesis wrote, so
it is ignored with a warning that says how to remove it.

B<Parameters:>

=over 4

=item C<$max_age>

The stale timeout in seconds.  Defaults to C<1800>, the older code's own.

=item C<$action>

Given by L</ensure_network_lock_held>, which checks again once this process
already holds its own lock: what this process was about to do, as a phrase
that follows "Cannot".  The refusal then says that an older Genesis appears
to have started deploying since this process took its lock.  Without it,
the refusal is about taking the lock.

=back

B<Returns:> Nothing, when the older lock is absent or stale.

B<Errors:>

=over 4

=item *

Dies when a fresh older lock is found.  The message names the director,
the holder's user, host, environment, and PID, when the lock was taken, the
vault path and URL, the likely cause, how long until the lock goes stale,
and the C<safe get> and C<safe rm -f> commands that check and clear the
key.

=item *

Dies when the exodus secret cannot be read, because a vault that refuses or
fails cannot be taken to mean that no older Genesis is deploying.  The
message gives the vault's reason, the likely causes, and the C<safe get>
and C<safe vault status> commands that check them.  A signal passes
through unchanged, for the caller's release to handle.

=back

B<Examples:>

  $self->_refuse_legacy_network_lock(1800);
  # Dies: Cannot take the network claims lock on the lab BOSH director: an older Genesis appears to be deploying against it. ...

=head2 _network_lock_token

  my $token = $self->_network_lock_token();

Returns the token that marks a network claims lock as this process's own.
It joins the hostname, PID, start time, and a random number, and is made
once per process and kept in C<%Service::BOSH::Director::NETWORK_LOCK_TOKENS>,
keyed by PID so that a forked child never passes for its parent.

B<Returns:> The token, as a string.

=head2 _refuse_network_lock

  $self->_refuse_network_lock($current, $lost_race);

Stops with a message saying that the network claims lock is held, and by

B<Parameters:>

=over 4

=item C<$current>

=item C<$lost_race>

B<Examples:>

=head1 KNOWN ISSUES

Defects that are still present. They are recorded so callers do not build
on the current, incorrect behaviour.

=over 4

=item errand-wrong-method-name (low)

C<run_errand()>: the error message says C<"Missing errand name in call to
deploy()"> but should say C<run_errand()>.

=item upload-config-asymmetric-bail (medium)

C<upload_config_from_file()> only calls C<bail()> on failure when invoked
in scalar or void context. In list context, a failed upload is silently
returned as C<($out, $rc, $err)> without any automatic error handling.
Callers in list context must check C<$rc> explicitly.

=item url-parse-no-validate (low)

C<new()> does not validate the C<url> option. If the URL is missing or
malformed, the regex silently produces C<undef> for C<schema>,
C<host>, and C<port>. The object is constructed with these undefined values
and subsequent calls to C<url()>, C<connect_and_validate()>, or C<status()>
will behave unpredictably.

=back
